# MQ 消费幂等性实施说明

本次只使用两种技术：数据库原状态条件更新（乐观锁）、数据库唯一消费记录与业务同一事务。未引入 Redis 去重、分布式锁、Outbox 或其他跨资源方案。

## 已实现

| 消费入口 | 使用方式 | 唯一范围 / 条件 |
| --- | --- | --- |
| 交易支付成功 | 乐观锁条件更新 | 订单 ID + `status = NO_PAY`，只有更新成功的调用继续更新明细并发送报名消息 |
| 交易退款结果 | 乐观锁条件更新 | 退款申请 ID + `status = AGREE`，成功、失败终态不被重复结果回退；只有有效迁移才继续更新明细和发送退课消息 |
| 学习支付加课 | 消费记录 + 业务同事务 | `(learning.lesson.pay, order:{orderId})`；一个支付订单的完整课程列表只执行一次 |
| 学习退款退课 | 消费记录 + 业务同事务 | `(learning.lesson.refund, order:{orderId}:course:{courseId})`；支持同一订单分批退不同课程 |
| 促销普通领券 | 消费记录 + 业务同事务 | `(promotion.coupon.receive, receive:{receiveRequestId})`；允许同一用户的多个合法领券请求 |
| 促销兑换领券 | 消费记录 + 业务同事务 | `(promotion.coupon.receive, exchange:{serialNum})`；兑换码状态从 UNUSED 条件更新；库存、用户券和兑换状态一起回滚 |
| 学习消费点赞总数 | 消费记录 + 业务同事务 | `(learning.qa.liked.times, message:{messageId})`；只保障同一传输消息的重复投递 |

课程、点赞服务没有有效 MQ 消费监听器，本次没有为它们添加消费者或改动生产逻辑。

公共执行器 `MqIdempotentExecutor` 由需要它的监听器显式 Import，不全局改变其他微服务的 MQ 配置。消费记录保存原消息体和 messageId，以 `(consumer_id, event_key)` 主键去重；成功记录只随业务一同提交，失败全部回滚。并发消费者依靠数据库唯一约束竞争，业务表的唯一键异常不会被误识别成已消费。

调用约束：执行器是消费事务入口，不能从已经开启的事务中调用；业务使用同一数据源、事务管理器和 REQUIRED 传播。不能在业务回调中以独立事务先提交数据库变更。

相关修复：

- 延迟查单在支付未成功时，调度下一轮后立即返回，不再错误进入支付成功处理。
- 构造下一轮延迟消息时复制 DTO 和延迟列表，不修改输入消息，避免本地重试跳过轮次。
- 支付成功入口校验结果，已关闭订单收到真实支付成功会抛业务异常，交由现有失败处理链路隔离/对账。
- 退款成功不会被迟到失败/处理中结果覆盖；失败后收到成功的矛盾终态会抛业务异常，需要核实。
- 乐观锁竞争失败时抛异常退出当前事务，在新事务重试时判断已处理状态，避免 MySQL REPEATABLE READ 的旧快照误判。
- 异步发起退款通过 Spring 代理调用，确保原有 `@Transactional` 生效。
- 加课查询结果缺失或不完整、课表/用户券/订单明细保存失败时抛异常，避免留下已成功消费记录。

## 部署前必须完成

1. 执行 [建表脚本](sql/mq-consume-log.sql)，在 `tj_learning`、`tj_promotion` 各创建 `mq_consume_log`。脚本不会在应用启动时自动执行。
2. 若之前手工使用设计文档中的示例 DDL 建过同名表，先核对并迁移成此次脚本的结构，尤其是 `message_id`、`payload`、`created_at` 及主键。`CREATE TABLE IF NOT EXISTS` 不会改造旧表。
3. 核对 MyBatis 与 JdbcTemplate 使用同一服务数据源和本地事务管理器；消费记录和业务表均使用 InnoDB。
4. 促销生产端的新消息携带 `receiveRequestId`，同次发布重试必须沿用该值；消费者兼容旧消息，旧普通领券只按原 `messageId` 去重。旧消息缺少 messageId 时抛异常，不生成随机替代键。
5. 蓝绿发布时先部署兼容新字段的消费者，再更新促销生产端；旧实例仍会重复执行业务，应退出旧实例后再开始验证保护结果。
6. 核对 Nacos 的 `shared-mq.yaml`：监听器不能使用 `acknowledge-mode: none`；事务异常必须进入重试/错误队列处理。当前仓库无法验证线上实际 ACK、重试参数。

不要删除仍可能重投、错误队列回放所对应的消费记录。已经运行过的历史业务没有自动生成凭据，旧消息第一次回放可能再次执行；上线前排空/隔离旧队列并对账，能够恢复业务身份的历史消息可补齐凭据。

## 无法完整保障的部分

这些问题保持明确边界，没有通过增加消费表或状态条件假装解决：

| 场景 | 原因及本次处理 |
| --- | --- |
| 签到、问答积分消费 | 一个处理同时写 MySQL 和 Redis `ZINCRBY`，本地事务不能原子回滚 Redis。两个入口保持原实现，没有宣称积分已幂等；QA 消息只有用户 ID，缺少回答 ID，签到缺少发生日期，也不能恢复稳定业务身份 |
| 支付/退款消费者继续发送 MQ | 状态与明细的本地数据库幂等已完成，但数据库提交与 broker 接收消息不原子。实际发布成功后数据库回滚、或异步确认失败等窗口仍存在；本次未实现可靠发送补偿 |
| 延迟查单派生下一轮消息 | 修复错误分支和输入对象变更，但重复消费仍可能派生多条相同轮次的查询。唯一消费记录与 MQ 发送不能同事务提交，因此没有用消费表丢弃重试并宣称可靠调度已完成 |
| 点赞快照首次乱序到达 | 消息只有业务 ID、总数，没有实体版本。已处理消息的原 messageId 重投会跳过；未处理过的旧快照或换 messageId 的旧快照仍无法可靠识别，也不能用最大总数过滤，因为取消点赞会减少总数 |
| 退款先到、支付后到，或首次迟到的旧退款遇到重新购买 | 当前课表没有原订单的权益归属。消费表可防止已执行事件重复，却不能决定不同事件的正确顺序或原订单权限；需要补充权益模型后再实现状态规则 |
| Redis 库存预占后领券消息发送失败 | 发生在生产端，Redis、MQ 和 MySQL 不原子；消费端发券防重不等于预占补偿与消息不丢失 |

其中，跨资源原子性超出本次两种技术的能力；缺少日期、回答 ID、快照版本或订单权益归属的情况，需要补全业务身份/模型，不能仅用用户 ID、消费时间或随机值作为唯一键。

## 验证

2026-10-15 验证结果：34 个新增测试通过；课程、交易、学习、促销、点赞五个服务及所需依赖模块编译通过。没有对实际业务数据库执行建表脚本。

新增测试覆盖：消费记录和业务共同回滚、同业务换 messageId 重发、不同逻辑消费者、并发竞争、首个消费者回滚后后续成功、业务唯一约束异常不被吞掉、分批退款、合法多次领券、点赞已消费快照重投，以及支付/退款状态竞争和失败回滚。

交易测试使用真实 MyBatis SQL、Spring 事务和 H2 MySQL 模式；公共执行器和监听器测试使用 H2 真实事务。没有依赖 Nacos 或外部 MQ 启动应用上下文。

```powershell
mvn -B -ntp -pl 'tj-trade,tj-learning,tj-promotion' -am `
  '-Dtest=MqIdempotentExecutorTest,LessonChangeListenerTest,LikeTimesChangeListenerTest,PromotionMqHandlerTest,PayServiceImplTest,TradeMqIdempotencyTest' `
  '-Dsurefire.failIfNoSpecifiedTests=false' test
```

使用 JDK 11。H2 测试不能代替实际 MySQL/InnoDB 锁行为及 RabbitMQ ACK/断线重投验收；部署环境还需执行这些检查。
